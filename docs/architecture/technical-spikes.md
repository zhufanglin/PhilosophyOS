# MVP 技术验证方案

## 1. 目的

在搭建完整应用前验证两个最高风险假设：

1. RAG 是否能生成可核对、不伪造的哲学回答。
2. 系统是否能安全读取、理解并在确认后写回 Obsidian。

验证只使用小型测试数据和合成仓库，不改动真实 `Stu的哲学思考`。

## 2. Spike A：可信哲学 RAG

### 2.1 用户结果

用户询问重点哲学家时，系统能引用具体来源、区分原典与解释，并在证据不足时拒绝乱答。

### 2.2 数据范围

- 哲学家：康德、斯宾诺莎、尼采。
- 每人 1 份合法原典片段和 2 份权威解释。
- 总片段控制在 200–500 个。
- 每个片段绑定版本、章节、来源等级、版权状态和内容哈希。

### 2.3 对比方案

| 方案 | 检索 | 生成约束 |
| --- | --- | --- |
| Baseline | 纯向量 top-k | 提示模型引用片段 |
| Hybrid | 关键词 + 向量 + rerank | 只允许引用返回片段 |
| Structured | Hybrid + 人物/著作/概念过滤 | 断言级证据检查 |

### 2.4 必测问题

- 康德如何区分自然因果与实践自由？
- 斯宾诺莎的自由是否只是认识必然？
- 尼采是否在《存在与时间》中谈论自由？
- 给出某一原文的具体页码，但不提供版本。
- 学界对物自体是否存在唯一共识？

### 2.5 通过标准

- `data/evals/cases.csv` 中引用相关 blocker 100% 通过。
- 直接引语逐字匹配率 100%。
- 断言引用覆盖率 >= 90%。
- Structured 方案的准确性优于 Baseline，且 P95 首次响应不超过 10 秒。
- 证据不足问题全部显示明确降级状态。

### 2.6 输出

- 三种方案的评测结果。
- 推荐检索架构和参数。
- 失败案例及修复策略。
- 进入正式知识库的数据清洗规则。

## 3. Spike B：Obsidian 安全闭环

### 3.1 用户结果

系统从测试仓库提取开放问题，生成符合用户格式的 Markdown 草稿，经确认后写入，并可撤销。

### 3.2 合成测试仓库

至少包含：

- 总览笔记。
- 3 篇主题笔记。
- 1 篇视频来源笔记。
- YAML、行内/列表标签、双向链接、提示块和待办项。
- 模拟 `.obsidian/plugins/example/data.json` 密钥文件，验证其永不被读取。

### 3.3 验证路径

```text
选择测试仓库
  -> 只读扫描 Markdown
  -> 提取“继续追问”和未完成任务
  -> 检索相关旧观点
  -> 生成 Markdown 草稿
  -> 展示结构化差异
  -> 用户确认
  -> 写入并记录审计
  -> 撤销写入
```

### 3.4 必测情况

- YAML 使用行内标签和列表标签。
- 双向链接目标尚不存在。
- 用户在确认页面打开后修改了原文件。
- 新文件编号与已有文件冲突。
- Local REST API 不可用。
- 文件只读或写入失败。
- 用户撤销最近一次 AI 写入。

### 3.5 通过标准

- `.obsidian` 和用户排除路径读取次数为 0。
- 开放问题提取准确率 >= 95%。
- Markdown 草稿保留 YAML、章节和链接结构。
- 未确认写入次数为 0。
- 内容哈希冲突全部阻止写入。
- 写入失败不损坏原文件。
- 撤销后文件与写入前哈希一致。

### 3.6 直接目录与 Local REST API 决策

两种接入方式均做最小实验：

| 方式 | 优点 | 风险 |
| --- | --- | --- |
| 直接目录 | 依赖少、可精确控制差异和原子写入 | 浏览器端访问本地文件受限，需要桌面桥接 |
| Local REST API | 与现有插件兼容、接口清晰 | 需要安全管理认证信息，并依赖 Obsidian 运行 |

选择标准：安装成本、权限透明度、写入原子性、冲突检测、Windows 稳定性和密钥安全。未完成对比前不在 PRD 中锁定唯一方案。

## 4. Spike C：好友房间权限与多人归属

### 4.1 目的

验证好友请求、私密讨论房间和多人观点总结不会造成越权访问或观点混淆。

### 4.2 最小范围

- 3 个合成用户。
- 好友请求接受、拒绝和拉黑。
- 1 个双人房间和 1 个三人房间。
- 服务端成员权限校验。
- 共同总结和每位用户独立个人总结。

### 4.3 必测情况

- 未接受好友请求时尝试发起讨论。
- 非成员获取房间、消息、引用或总结。
- 用户退出后尝试读取新消息。
- 一位用户拉黑另一位用户。
- 两位参与者表达相反观点，AI 生成总结。
- 用户只分享观点卡片，但系统尝试读取其原始 Obsidian 笔记。

### 4.4 通过标准

- 越权访问全部返回拒绝且不泄露房间元数据。
- 多人观点归属正确率 100%。
- 共同总结不会自动进入个人记忆。
- 拉黑后新请求、邀请和直接互动全部阻断。
- 分享上下文仅包含用户确认的具体快照。

## 5. 实验顺序

1. 先完成 Spike B 的只读解析和草稿生成，因为它直接验证个人工作流。
2. 并行准备 Spike A 的合法小型资料集。
3. 完成 RAG 三种方案对比。
4. 在合成仓库上连接 RAG 与笔记草稿。
5. 单人闭环稳定后执行 Spike C，不与初始 MVP 并行扩张。
6. 评测全部通过后，才申请对真实仓库进行只读试运行。

## 6. Spike D：云同步、计费与运维地基

### 6.1 目的

验证 PhilosophyOS 从本地 Beta 迁移到商业化云服务时，账号隔离、成本控制、数据恢复、审计和合规是否能同时成立。这个 Spike 不追求完整 SaaS，而是验证上线前最容易变成阻断点的基础设施。

### 6.2 最小范围

- 3 个合成用户、2 个工作区、1 个付费订阅、1 个欠费订阅。
- 云 PostgreSQL 原型，包含 `user_id`、`workspace_id`、membership、model profile、dialogue、snapshot、export audit。
- 对象存储原型，保存导出包、用户上传材料、支持包，全部带 workspace 前缀。
- 额度账本，记录模型调用次数、估算 token、供应商、模型、成本归属。
- 备份与恢复演练，至少覆盖数据库恢复和对象存储恢复。
- 运维审计，至少覆盖登录、模型配置变更、导出、删除、写入 Obsidian、撤销写入。

### 6.3 必测场景

- 用户 A 无法读取用户 B 的工作区、导出包、模型配置和对象存储路径。
- editor 不能修改账单、删除工作区或导出全量数据。
- 欠费工作区可以读取已有档案，但不能继续产生平台付费模型调用。
- 用户自带 Key 的工作区不进入平台成本账单，只记录用量和错误状态。
- 平台托管 Key 的调用必须进入额度账本，并能按 workspace 聚合成本。
- 导出包不包含完整 API Key 或加密 envelope。
- 删除工作区后，私有数据不可访问，公共哲学数据不受影响。
- 恢复最近一次备份后，审计记录能解释恢复窗口内可能丢失的数据。
- 监控告警能发现 API 错误率升高、供应商限流、成本异常、备份失败。

### 6.4 通过标准

- 所有私有查询都强制带 `workspace_id` 过滤，越权测试通过率 100%。
- 计费账本能按 workspace、provider、model、day 汇总用量和估算成本。
- 欠费/超额时仍保留只读访问和数据导出，不静默删除用户数据。
- RPO 目标不超过 24 小时，RTO 目标不超过 4 小时，并有恢复演练记录。
- 审计日志覆盖高风险动作，且不保存完整正文、API Key 或 provider headers。
- 合规文档至少包含隐私政策、数据删除说明、数据导出说明、供应商清单。

### 6.5 停止条件

- 无法保证 workspace 隔离时，不上线账号系统。
- 无法按 workspace 统计模型成本时，不上线平台托管 Key 或订阅计费。
- 无法恢复数据库和对象存储的一致状态时，不开放云同步。
- 无法解释数据删除范围时，不开放团队或公开分享功能。
- 无法确认供应商数据使用边界时，不上线默认托管模型套餐。

## 7. 停止条件

- 无法可靠阻止未确认写入时，停止 Obsidian 集成开发。
- 无法绑定具体来源版本时，不开放直接引语功能。
- 来源版权状态不清楚时，只使用元数据进行实验。
- 小型知识库仍频繁伪造引用时，先修复证据约束，不扩大人物范围。
- 服务端无法可靠执行房间权限或多人观点归属时，不开放好友讨论。
